# Порядок зміни стандарту

1. Будь-який учасник або рецензент подає issue зі схемою STD-номер; одноосібна навчальна команда не вигадує голосування неіснуючих людей.
2. Пропозиція містить ID, рівень, причину, поганий/добрий код, спосіб перевірки, перелік файлів міграції та оцінку часу у годинах із припущеннями.
3. Власник стандарту Чугаєв Олексій Михайлович приймає рішення після рев’ю; у майбутній команді потрібні власник модуля й хоча б один незалежний рецензент. Рішення спирається на дефекти, читабельність та вартість переходу; за відсутності згоди чинне правило зберігається.
4. Результат фіксують ADR з номером, датою, статусом, альтернативами, наслідками та посиланням на PR. Відхилені пропозиції теж лишаються в журналі.
5. Версія стандарту семантична: підвищення обов’язковості або несумісна конвенція — major; нове сумісне рекомендоване правило — minor; уточнення без зміни вимоги — patch. Застосунок версіонується незалежно.
6. Для старого коду діє бойскаут: змінений файл стає чистішим у межах задачі. Обов’язкову міграцію планують окремо з кінцевою датою, не безстроковим винятком. Поточний реєстр: STD-201 — проєктування партій і доз, власник Чугаєв, перегляд до 21.12.2026; STD-202 — змістовні XML-коментарі старого Core та оцінка всіх ручних метрик, той самий власник і дата.
7. Шкідливе правило скасовують новим ADR з виміряним або відтвореним дефектом; номер не перевикористовують. Відкат конфігурації проходить той самий CI та містить план повернення або заміни перевірки.
